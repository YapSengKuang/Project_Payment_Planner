# Sprint 2 expenses payments and Google sign-in

## Goal

An owner can enter, save, reopen and revise a project's expected costs and client receipts. Incomplete payment totals remain saveable drafts with a visible explanation. Google sign-in supplements email links.

## Implemented features

- Google OAuth sign-in via Supabase, email fallback, provider-start errors and cancelled/failed callback messaging. The same authenticated user ownership rules apply.
- Project navigation between Setup, Expenses and Milestones. Pending saves/deletes disable navigation to avoid overlapping changes.
- Expense create/edit/delete: description, positive AUD amount and expected payment date. Deletion requires a confirmation.
- Deposit and milestone create/edit/delete: type, name, positive amount, completion/deposit date, invoice date and calendar-day payment terms.
- Invoice date initially follows completion/deposit date, but can be changed independently. Expected receipt is generated by the database from invoice date plus terms, or an explicit override with its reason.
- Saved schedule summary: project price, total expected receipts, total expenses and under/overallocation. Exact matching payments mark the payment schedule complete; incomplete totals never block saving a valid entry.
- Database constraints, per-project ownership policies, immutable project links and metadata. Project GST convention is fixed while any expenses or milestones exist. No change to existing project ownership.

## Product conventions

AUD only; amounts use integer cents, with the same limits as project setup. Every schedule entry follows the project's GST convention. Dates are date-only calendar values. Terms are whole calendar days from 0 to 365; weekends count. Receipts may occur after project end, and costs or deposits may precede project start. Completion does not imply invoicing or payment. These conventions are provisional pending customer validation.

A manual receipt date requires a reason of 1 to 500 characters. Turning the override off clears both override fields and restores the calculated date. Partial payment schedules can be saved as drafts, including temporary overallocation. Completion is derived from the latest saved entries and current project price; it is not a promise of available cash or confirmation of receipt.

The schedule loader pages database results, rather than relying on the API's first page. More than 10,000 entries per table per project produces an explicit load error instead of misleading partial totals.
